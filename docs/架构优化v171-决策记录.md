## 已实施（按投入产出比排序）

### ① keyword_scores 三遍算 → 参数透传复用
- **证据**：`core/extract_engine.py` 的 `extract_core` 先算 `global_scores`，
  随后 `sentence_vectors(sents)`（内部再算一遍）和 `top_keywords(...)`（第三遍）。
  `core/iterate_engine.py` 同样重复。
- **改法**：给 `sentence_vectors` / `top_keywords` 加可选 `global_scores` 参数，
  调用方传入已算好的结果；不传时行为完全不变（向后兼容）。
- **等价性**：实测句向量与关键词逐字相等；`extract_core` 的 points/keywords 相等，
  只有 `stats.elapsed` 变化（预期）。
- **决策理由**：数值零变化的纯优化，风险最低，优先做。

### ② platform.platform() 高频重算 → 进程级缓存
- **证据**：`app.py` 注释明确 `/api/state` 是 400ms 高频轮询端点；
  实测 `platform.platform()` 单次 **0.83ms**，是 `python_version()`（0.004ms）的 **200 倍**，
  而在进程生命周期内该值恒定。
- **改法**：模块级 `_platform_label()` 惰性缓存。
- **决策理由**：高频 + 恒定 + 实测有开销，典型该缓存未缓存。

### ③ provenance_media.json 非原子写 → 加锁 + 原子替换
- **证据**：`media/media_runtime.py::write_provenance` 直接 `target.write_text()` 覆盖；
  音视频/OCR 多能力可能并发写同一文件，读方可能拿到半截 JSON。
- **改法**：`threading.Lock` 串行化 + 临时文件 `os.replace()` 原子替换
  （复用 `app.py::_save_settings` 的既有范式）。
- **决策理由**：这是**正确性 bug** 而非单纯优化；修复面小、收益确定。

### ④ knowledge 逐条入库 → executemany 批量
- **证据**：`knowledge/kb.py::ingest_md` 对每条条目做 1 次 SELECT + 1 次
  INSERT/UPDATE + 1 次 FTS INSERT，N 条 = 3N 次 execute。
- **改法**：一次性读已有 id 集合；新条目 / 重复 id 分别 `executemany`；
  保持"同文件内重复 id 判 dup 且 ref_count+1"的时序语义
  （UPDATE 必须在 INSERT 之后执行，否则同批次首次插入的行还没存在）。
- **验证**：构造 2 条锚点的 md，入库两次：
  第一次 `added=2/dup=0`，第二次 `added=0/dup=2`，ref_count 正确累加到 2；
  300 条批量入库 0.12 秒。
- **决策理由**：中等改动面，但语义已用针对性用例锁死，收益明确。

## 明确推迟（决策：不做）

### ⑤ link_guard DNS 解析加超时
- `link/link_guard.py:113` 的 `socket.getaddrinfo` 确实无超时，域名失效时可挂住线程。
- **推迟理由**：这是 **SSRF 防护的安全敏感路径**，标准库无直接超时参数，
  正确做法需要引入线程池或信号机制，复杂度与风险都高，且非当前用户痛点。
  为避免"为优化而优化、反而破坏防护语义"，本轮不动。

### ⑥ app.py 39 处 `except: pass`
- 多数是 UI 增强/可选能力的诚实降级（契约 §6 要求"缺工具显式降级、不假成功"），
  盲目改成抛异常会破坏既有降级契约。逐条甄别成本高、收益不确定，本轮不动。
