## 一、严重（建议修复后再发版）

### 1. api_key 掩码回填后，一次「保存」即把真 key 覆盖成掩码

- 位置：`ui/app.js:1453`（回填掩码进输入框）+ `ui/app.js:1498`（原样提交输入框值）+ `backend.py:120-122`（仅空串才保留原 key）
- 现象：用户配置好云端 key 后，`public_config()` 回显掩码（如 `****3456`）被填入输入框；此后**任意一次保存**（哪怕只改补写开关或模式），掩码串被当成新 key 写入，真 key 永久丢失，云端后端全部 401。
- 实测证据：

```
第 1 次保存后真 key = sk-REAL-KEY-abcdef123456
UI 回显 api_key    = ****3456
第 2 次保存后真 key = ****3456        ← 被掩码覆盖
>>> key 被掩码覆盖？ True
```

- 修复建议（二选一或同时做）：
  - 前端：提交前若输入框值与 `r.config.api_key`（掩码）相同，则提交空串（走后端「空值保留」语义）；
  - 后端：`save_config` 里若 `incoming["api_key"] == mask_key(current_key)`，视为「未修改」保留原 key（防御性兜底）。

### 2. `top_keywords` 标题词位置跨度造假 → 标题词全军覆没，关键词输出碎片垃圾

- 位置：`extract_engine.py:321-322`
  ```python
  pos = sents[0]["text"].find(term)          # 只在【第一句】里找位置
  items.append((term, w, max(pos, 0), max(pos, 0) + len(term)))
  ```
- 现象：标题挖词（`heading_terms`）本是可靠词源，但其跨度被硬凑到 `sents[0]` 开头。找不到时 `pos=-1` → 跨度塌缩为 `(0, len(term))`，**所有标题词的跨度互相重叠**，`pick_terms` 槽位冲突消解只留 1 个、其余全部误杀。
- 实测证据（标题含「数据一致性保障机制 / 技术架构分层设计 / 隐私保护约束」）：

```
标题挖词 heads    = ['技术架构', '技术架构分层设计', '数据一致', '数据一致性保障机', '隐私保护', '隐私保护约束']
top_keywords     = ['一致性', '隐私', '来源', '层设', '全分', '全系', '心约', '析安']
标题词入选        = []        ← 6 个标题词 0 个入选，名额被二元组碎词（心约/析安/全分）占满
```

- 影响：不触及「不造假」红线（核心条目文本仍是原句），但产物「关键词：…」与评分依据质量崩坏。
- 修复建议：标题词应在**实际命中的句子里** `find` 真实位置参与消解；找不到真实位置的词不应携带假跨度（可按频次直接入选或用独立通道不参与槽位消解）。

### 3. B 档产物「本次改写操作」行静默丢失（replace 目标串不匹配，死代码）

- 位置：`refine.py:549-553`（replace 的 old）vs `extract_engine.py:692-694`（render_md 实际输出）
- 现象：`_run_revise_extract` 想把保真度行替换为「保真度 + 本次改写操作」两行，但 `render_md` 在 `mode` 含「改写」时**已经输出**新保真度文案，old 串（"…每条核心均为原文原句，可逐字定位"）根本不存在于文本中 → `str.replace` 静默无效果。
- 实测证据：渲染产物中 `含'本次改写操作': False`，操作说明行（术语归一/合并去重/结构重排 + 合并条数）从未出现在任何产物里。
- 修复建议：直接把 old 改为 render_md 实际输出的 is_rewrite 文案，或给 `render_md` 增加 `ops` 参数原生输出该行（后者更稳，避免字符串耦合）。

## 二、中（功能缺口 / 一致性问题）

### 4. LLM 模式真实推理未接入：`chat()` 是空心位，AI 补写真实环境跑不了

- 位置：`backend.py:177-178`（基类 `chat` 抛 NotImplementedError）；`LocalBackend` / `CloudBackend` **均未实现 `chat()`**（grep 全项目仅 mock 测试里有实现）。
- 现象：切到 LLM 模式 + 配好 ollama/云端 + 点精读/修订 → `refine.py:317` 重新抛出 → 任务报「提纯失败：NotImplementedError」。S8c 的 AI 补写同理，仅被 mock 测试（test_54 FakeLLM）覆盖。
- 性质：属**阶段边界**（`test_48` 显式断言 `CloudBackend.chat` 抛 NotImplementedError，docstring 也写明「留 S7b 后半」），诚实性没问题（绝不返回假结果）；但用户视角是「开关都在、功能点了报错」。
- 建议：作为下一阶段（S7b 后半 / S9）正式接入 `POST /chat/completions`（本地 ollama 与云端同协议、超时/错误脱敏沿用 `_http_get_json` 口径），届时同步改 test_48 的预期；接入前建议在 UI 的 LLM 模式说明里明示「真推理尚未接入」，避免误导。

### 5. extract 模式修订产物 doc_id 与精读产物断链

- 位置：`refine.py:546`（`_extract.render_md` → `media_runtime.source_info(src)` 按 **refine.md 内容哈希**取 doc_id）对比 `refine.py:647-648`（LLM 路径从**文件名**提取 doc_id 保持一致）。
- 实测证据：`doc_aaaaaaaaaaaa.refine.md` → extract 修订产物 doc_id 为 `doc_857304eb170f`（≠ `doc_aaaaaaaaaaaa`），产物名 `doc_8573….revise.md`；而 LLM 路径会产出 `doc_aaaaaaaaaaaa.revise.md`。同一功能两种模式命名行为不一致，用户按 doc_id 追链条会断。
- 修复建议：`_run_revise_extract` 与 LLM 路径对齐——优先从 `src.name` 提取 `doc_[0-9a-f]{12}`，取不到再回退内容哈希。

### 6. B 档合并条目的多块 anchor 不能被 `parse_core` 解析（链式处理丢核心）

- 位置：`extract_engine.py:675-676`（渲染 `<!-- anchor: doc_x | block: 2 | blocks: 2,7 -->`）vs `revise_engine.py:51`（`_ANCHOR_RE` 要求 `block:\s*(\d+)\s*-->`，多块格式不匹配）。
- 实测证据：含多块 anchor 的文档 `parse_core` 只解析出单块条目（多块条目整条丢失）。
- 影响：当前主流程（修订输入限 `.refine.md`，单块格式）不受影响；但 B 档产物再加工、或未来链式修订会静默丢核心。
- 修复建议：`_ANCHOR_RE` 兼容可选 `| blocks: …` 尾巴；`parse_core` 把 `blocks: 2,7` 解析为块列表。

### 7. `allow_suppplement` 字符串强转陷阱：`"false"` → `True`

- 位置：`backend.py:80`、`app.py:2423`（`bool(data.get("allow_suppplement", False))`）。
- 实测证据：`save_config({"allow_suppplement": "false"})` 后配置为 `True`——补写开关被**误开启**（补写是「原文外生成」的敏感开关，方向上不该朝开误转）。
- 影响：前端 JS 传的是真布尔，UI 路径无恙；仅直接调 API / 旧客户端 / 脚本会踩中。
- 修复建议：只有「值是 bool True 或字符串 "1"/"true"/"yes"（不区分大小写）」才判开，其余一律关（默认关的语义要保守）。

## 五、测试补强建议（防回归）

1. **掩码往返**：保存真 key → `public_config` 掩码回填 → 再保存 → 断言真 key 未被覆盖（当前会红，修 #1 后转绿）。
2. **top_keywords 标题词**：构造含 2+ 个标题的文档，断言标题词至少入选 1 个、且输出关键词不含纯二元组碎词（修 #2）。
3. **B 档操作行**：断言产物含「本次改写操作：」行（修 #3）。
4. **多块 anchor 解析**：`parse_core` 对 `| blocks: 2,7` 格式断言解析出块列表（修 #6）。
5. **doc_id 命名**：extract 修订产物文件名断言与精读产物 doc_id 一致（修 #5）。
6. **补写开关类型**：`allow_suppplement="false"` 字符串断言保存为关闭（修 #7）。
