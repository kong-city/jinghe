# CID 乱码 PDF 的可补救诊断（v1.6.3 后处理层改进）

> 日期：2026-11-24
> 触发：用户运行扫描版 PDF（《Python.Unix 和 Linux 系统管理指南》）后，
> 对账清单显示「成功 0」，归因写的是「markitdown 因 onnxruntime 崩溃不可用」。

---

## 一、现场诊断（实测，非推测）

| 项 | 实测值 |
|---|---|
| PDF 页数 | 431 页 |
| 含图像页 | 426 页 |
| 有文字层页 | 5 页 |
| 内置解析抽出字符 | **1,767,951**（全是乱码 `\x90\x03È...`） |
| 假成功门禁 | 正确拦下（未产出乱码文件）✓ |
| OCR 组件 | 已装，但 `onnxruntime_pybind11_state` DLL 初始化失败 → `available=false` |

**结论**：这不是"markitdown/onnxruntime 崩溃"导致的——真因是 **CID 子集字体的
ToUnicode 映射不完整**，内置解析把 GID 字节误当文本解出 176 万乱码字符，
被质量门禁正确拦下。

## 二、之前的两个真问题

1. **静默**：`app.py` 的 OCR 后处理在组件不可用时整段跳过，用户除了内核那句
   误导文案，看不到任何"可以做什么"的提示。
2. **归因错**：内核文案把失败甩给 markitdown/onnxruntime，用户会去重装它们，
   白忙一场。

> 修正一处早期判断：OCR 后处理此前**并非**只对"无文字层"触发——它对每个 PDF
> 都调用 `ocr_pdf_to_md`，由该函数按"产物是否已存在"决定跳过。所以本例在组件
> 可用时本就能 OCR，缺的是"组件不可用时的诊断与引导"。

## 三、改法（守冻结内核契约）

`docs/CAPABILITY_CONTRACT.md` §1 不变量：`extract.py` 探测/分流/提取/汇总/对账
主流水线一行不动。因此**不改内核**，只在 L4 后处理层（`app.py`）补两个函数：

- `_ocr_degraded_names(outdir)` —— 只读 `provenance.json`，找出状态含
  「需专用解析器 / 需先 OCR / 疑似扫描件」的 PDF 文件名；不写任何文件。
- `_ocr_guidance(available, reason)` —— 准确诊断文案：真因是 CID/ToUnicode，
  与 markitdown/onnxruntime 无关；组件可用则提示将自动识别，不可用则引导去
  「设置 · 组件」启用「扫描件 OCR」并带上真实失败原因。

后处理块逻辑：组件可用 → 原 OCR 流程照跑；组件不可用但对账里有降级 PDF →
逐条输出诊断日志（`job.add("log", ...)`，UI 日志面板可见）。

**冻结内核 `extract.py` / `SPEC.md` 零改动**；内核产出的 INDEX.md / MERGED.md
清单文件保持原样（诚实降级不变）。

## 四、未做（需单独评估）

**C：修 onnxruntime 组件** —— 组件虽已安装，但 DLL 初始化失败。重装修补可能
需换版本 / 装 VC++ 运行库 / 联网下载，有环境风险，未在本轮改动内。修好它后，
本例就能真正自动 OCR 出 431 页正文。
