# 发版流程：远端打包约定

> 确立日期：2026-11-23（用户裁决）
> 适用范围：`jinghe-desktop` 主线所有版本更新

---

## 一、约定内容（一句话）

**本地打的包只用于本地验证与自用，不上传 GitHub；每次版本更新都要推 `v*` tag，让 GitHub Actions 在远端重新打包，Release 资产只认 CI 产物。**

这条约定取代了早期「本地打包后手动上传 Release」的做法（`for-upload` 门禁、手动 `gh release upload` 等已废弃）。

## 二、为什么这样定

| 维度 | 说明 |
|---|---|
| **产物可信** | 远端 Release 由 CI 从当次 tag 的源码完整构建，可复现、可审计，不掺入本机环境差异 |
| **版本一致** | CI 内构建后端 exe + 安装包 + `latest.yml` 一气呵成，`sha512` 与文件名天然匹配，不会出现本地包和元数据对不上 |
| **带宽成本** | 85MB 安装包从本机传 GitHub 极慢（实测 6 分钟仅 5%）；CI 在境外上传，秒级完成 |
| **自更新正确** | `electron-updater` 依赖 `latest.yml`，它必须由产出安装包的同一次构建生成 |
| **职责清晰** | 本地打包 = 开发验证；CI 打包 = 正式发版。两条路径互不干扰 |

## 三、标准发版流程（每次更新都走）

### 路径 A：一键发版（推荐）

```bash
# 1. 升版本（唯一真源 + 6 派生点同步，自动联网避开撞号）
python tools/bump_version.py patch --reason "本次改动说明"

# 2. 本地验证（不上传！）
python tools/check_release.py --no-exe

# 3. 一条命令完成：提交 → 打 tag → push → 监控 CI
python tools/release.py --reason "本次改动说明"
```

`release.py` 会在动手前检查：门禁是否通过、工作区是否干净、`v<版本>` tag 是否重复、本地是否落后远端；并支持 `--dry-run` 先看会执行什么。

### 路径 B：手动发版

```bash
# 1. 升版本 + 本地验证（同上）
python tools/bump_version.py patch --reason "..."
python tools/check_release.py --no-exe

# 2. 提交并推送源码
git add -A
git commit -m "release(vX.Y.Z): 本次改动说明"
git push origin main

# 3. 打 tag 并推送 —— 这一步触发远端打包
git tag -a vX.Y.Z -m "精核 vX.Y.Z：本次改动说明"
git push origin vX.Y.Z
```

## 四、CI 收到 tag 后做什么

`.github/workflows/ci.yml` 的两个 job：

1. **test job**（push main 和 push tag 都会跑）
   语法检查 → 全套 251 单元测试 → 发版门禁。
2. **release job**（仅 `if: startsWith(github.ref, 'refs/tags/v')`）
   构建后端 exe → 校验产物版本 → 构建 Electron 安装包与 `latest.yml` → 冒烟验证 →
   `gh release create` + 上传三资产（`--clobber` 覆盖）。

**关键**：`push main` 只跑测试、不发包；**只有 push `v*` tag 才触发远端打包**。
所以「更新了代码但忘了打 tag」= 没有发版，Release 不会动。

## 五、本地包的定位

本地仍可打包，用于：

- 改完代码后验证安装包能否正常启动、图标/托盘是否正确；
- 离线环境或内网机器上自用安装。

本地打包命令见 [本地打包指南.md](本地打包指南.md)。
注意本地包与 CI 包的字节数可能略有差异（构建环境、时间戳、压缩元数据不同），
**版本与内容一致**，但正式发布的一律是 CI 产物。

> 本地包放桌面（如 `C:\Users\songweihu\Desktop\Jinghe-X.Y.Z-setup.exe`）即可，
> **不要**手动传到 GitHub Release。

## 六、注意事项与常见坑

1. **tag 一旦推送就会触发 CI**，打之前确认版本号已升、门禁已过。
2. **tag 指向的提交必须包含当次改动**：先 commit/push main，再打 tag；顺序反了 CI 会构建到旧代码。
3. **不要复用已有 tag 名**：同名 tag 推送不会触发新的构建事件。发版号冲突就升 patch。
4. **test job 失败会阻塞 release**（`needs: test`）。CI fresh checkout 与本地环境不同，
   曾出现「本地过、CI 挂」的冻结护栏假失败（test_59），已修复；新增测试时注意不要在
   断言里依赖本地残留文件。
5. **旧 Release 清理**：历史版本按用户裁决只保留最新一个。清理是破坏性操作，
   需单独确认后执行（用 GitHub API DELETE，不要删 tag）。
6. **残留 tag**：失败的 `v1.3.3` tag（无对应 Release）保留作为版本标记，不影响自更新。

## 七、发版后验证清单

- [ ] CI run 状态 `success`（test + release 两个 job 都是绿的）
- [ ] GitHub Release 页面出现新 tag，三资产齐全：
  `Jinghe-<版本>-setup.exe` / `Jinghe-<版本>.exe` / `latest.yml`
- [ ] `latest.yml` 里的 `version` 与 tag 一致，`sha512` 对应新安装包
- [ ] 本地 `git status` 干净，`git ls-remote origin HEAD` 与本地一致
- [ ] 桌面安装包版本与远端一致（本地打包替换即可，无需上传）
