## 2. 功能边界（两阶段，做什么 / 不做什么）

### 2.1 阶段一「精读」= 提纯核心知识点
- 输入：用户已转换好的 `.md`（来自 `out/md/*.md` 或合并文档 `MERGED.md`），**只读**
- 动作：调用本机大模型做**语义级提纯**（不是抽取首段），产出核心知识点 / 结构脉络
- 产物：`out/derived/<doc_id>.refine.md`
- **只提纯，不补写、不修改**——补写/修改是「修订」阶段的职责

### 2.2 阶段二「修订」= 补写缺失 + 修改核心
- 输入：阶段一的 `.refine.md`（核心知识点文档），只读原核心
- 动作 A「补写」：对核心知识点缺少的内容，由大模型补充（背景 / 术语 / 关联概念 / 遗漏要点）
- 动作 B「修改」：对已有核心内容做改写（更准确 / 更通顺 / 纠错）
- **关键约束**：所有"补写"和"修改"的内容，**必须与原文核心有视觉区分**（见 §4.3 双产物）
- 产物：`out/derived/<doc_id>.revise.md`（符号标记）+ `out/derived/<doc_id>.revise.html`（彩色样式）

### 2.3 不做什么（红线）
1. **绝不编造原文没有的事实**：精读提纯必须可回溯到源 md 的块级锚点；修订补写必须**显式标注"模型补写"**，与"原文核心"分区，不得冒充原文
2. **区分必须可靠**：每一处新增 / 修改都要能被样式标记捕获；**不得出现"改了却没标记"的内容**——这是本能力最核心的红线
3. **不写空壳**：解析不出内容 / 模型无响应 / 分段为空 → **零产物**，不写"核心：无"或"本次无需修订"的占位文档
4. **不碰冻结对账盘**：只读 `out/md/`、`MERGED.md`、`INDEX.md`；**绝不写入**这些位置（保护 SPEC §3.F 双向件数对账）
5. **不自动下载模型**：whisper 模型都不预下，大模型权重更不随软件分发、不自动拉取
6. **不改任何既有端点**：`/api/summarize` / `/api/transcribe` 空心位 / 其他端点契约全部原样
7. **隐私随后端而定**：Local 后端内容不出本机；Cloud 后端内容会外传，**须客户在设置中显式配置端点+key 即视为知情同意**；两者都不配置则能力未启用、零产物

## 4. 产物契约

### 4.1 存放位置（沿用 S0 关键裁决）
- 精读产物：`out/derived/<doc_id>.refine.md`
- 修订产物：`out/derived/<doc_id>.revise.md` + `out/derived/<doc_id>.revise.html`
- **绝不**写 `out/md/*.md` / `INDEX.md` / `MERGED.md`
- `derived/` 惰性创建；空输入 / 缺工具零副作用（连目录都不建）

### 4.2 精读文档结构（三区块 + 8 字段来源注释）
```
<!-- 精核 · 精读文档（核心提纯） -->
<!-- src: file=<源md> | doc_id=<...> | model=<工具名+版本> | ... 8 字段来源注释 -->

## 文档信息
（源文件、生成时间、模型、参数）

## 核心知识点
（语义级提纯的核心观点 / 结构脉络；每条可回溯到源 md 的块级锚点）

## 提纯元数据
（模型名+版本、分段数、是否部分成功）
```

### 4.3 修订产物：双产物 + 样式区分（本次新增的核心）

**为什么双产物**：Markdown 原生不支持颜色。为同时满足"通用可读"与"颜色区分"，产出两份：

#### (a) `revise.md` —— 纯文本，符号标记（通用可读）
用成对符号标记变更，任何 md 阅读器都能看出差异：
```
<!-- 精核 · 修订文档（符号标记版） -->
<!-- 图例：[++ 新增 ++] 模型补写 ｜ [[~~ 原文 ~~ → 修改]] 模型修改 ｜ 无标记 = 精读原文核心 -->

## 核心知识点
无人值守的本地文件处理是本次重点[++，尤其注重隐私与零依赖++]。
[[~~必须联网才能提取~~ → 全程离线可用]]。

## 修订元数据
（模型、新增段数、修改段数）
```
- 标记语法需**成对且唯一**，便于程序校验"每一处变更都被标记"
- 纯文本 md 里没有真实颜色，靠符号区分；图例固定写在文档头

#### (b) `revise.html` —— 带颜色样式（查看用）
- 纯标准库拼装（不引外部依赖），不复用 S2b docx 逻辑
- 颜色方案（遵循 WCAG AA，正文对比 ≥4.5:1，与首页可访问性审查一致）：

| 类型 | 样式 | 颜色 |
|---|---|---|
| 原文核心 | 正常黑字 | `#1F1F1D` |
| 模型补写（新增） | 绿字 + 浅绿底 | 字 `#1F6B3B` / 底 `#EDF7F0` |
| 模型修改（旧） | 红色删除线 | `#A32D2D` |
| 模型修改（新） | 蓝字 | `#185FA5` |

- html 头部放**图例**，明确每种样式的含义 + "内容由模型生成，请核对"
- 用内联 `<style>`（单文件、可直接双击打开），不引 CDN、不引外部字体

#### (c) 标记→样式映射的可靠性（红线 2 的落实）
- 修订引擎内部用**结构化变更列表**（每条：类型 add/modify、原文、新文、位置锚点）作为单一真源
- `revise.md` 与 `revise.html` **都由这份变更列表渲染**，不从其中一份反推另一份——保证两份标记一致
- 交付前校验：变更列表里的每一条都能在两份产物中找到对应标记；对不上则判失败、零产物
- **可行性已验证（契约阶段一次性原型）**：用 4 条变更（plain/add/modify/plain）同源渲染两份产物，逐条校验全部找到对应标记 → PASS；符号标记与彩色样式的映射方案可落地，无需在契约阶段再质疑

### 4.4 provenance
- 追加写入 `out/derived/provenance_refine.json`（读旧追加、不覆盖历史）
- 每条记录：源 md、doc_id、阶段（refine/revise）、模型名+版本、生成时间、提纯/新增/修改各自分段数、是否部分成功、两份修订产物路径

## 5. 可插拔后端适配器契约（方案 C · 2026-11-16 改定）

### 5.1 统一接口
```
Backend.probe()        -> {available, kind, reason}       # 探测可用性
Backend.list_models()  -> {ok, models: [...], error?}     # 列出可用模型
Backend.chat(messages) -> str                             # 实际推理（S7b 后半实现）
```
`refine.py` 只认 `Backend` 接口，不知道后端是本地还是云端。

### 5.2 两个实现
| 实现 | 端点来源 | 内容去向 | 客户成本 |
|---|---|---|---|
| **LocalBackend** | 固定 `http://localhost:11434`（ollama） | 不出本机 | 客户自选装 ollama + 模型 |
| **CloudBackend** | 客户填的 OpenAI 兼容端点 + key + 模型 | 外传（客户配置即知情同意） | 零安装，联网按量付费 |

两者走**同一套 OpenAI 兼容 `/chat/completions` 协议**，底层 HTTP 调用共用；差别只在端点来源、鉴权头、探活方式。

### 5.3 配置与密钥（关键安全约束）
- 后端独立存 `%LOCALAPPDATA%\Jinghe\backend.json`，**不放 settings.json**——后者被 `/api/settings` 明文回显、且可被日志导出端点触及
- 密钥字段 `api_key`：**只读配置端点一律脱敏**（回显 `****` + 后 4 位），POST 更新时新值覆盖、空值不改；**绝不写进日志、provenance、产物、异常堆栈**
- 客户不配置 = `probe()` 返回 unavailable = 能力未启用、零产物（与 S7a 现状一致）
- 软件本体不打包任何端点/密钥默认值

### 5.4 隔离与探测
| 项 | 约定 |
|---|---|
| **不进 TOOL_SPECS** | 后端探测独立挂 `refine.capability()['tools']['backend']`，**绝不并入 `media_tools.TOOL_SPECS`**（S1 契约锁死 3 工具 + 占位清单） |
| probe 顶层字段 | `/api/tools/probe` 顶层 `refine` 字段增 `backend` 子结构（kind / available / reason），不改 tools 结构 |
| 缺配置语义 | 未配置后端 / 探测失败 → `capability: "unavailable"` + 提示，UI「未启用」，**零产物** |
| 超时/取消 | 长任务独立 Job（不污染阶段 1 `/api/progress`）+ watchdog；推理数十秒给明确提示 |

## 9. 风险登记（先挂账，不承诺消除）

1. **模型幻觉**：补写/修改可能生成似是而非的内容 → 靠"分区呈现 + 显式标注模型生成 + 核心可回溯锚点 + html 图例提示核对"缓解，但无法根除
2. **标记遗漏（本能力最核心风险）**：若某处变更没被样式捕获，用户会误以为是原文 → 靠"结构化变更列表单一真源 + 双产物同源渲染 + 交付前逐条校验"缓解；校验不过则零产物
3. **大模型质量参差**：本地小模型（如 7B）的提纯/改写质量有限 → 诚实展示模型名，用户自行判断
4. **长任务耗时**：CPU 推理可能数分钟 → 独立 Job + 进度 + 取消，不阻塞 UI
5. **云端端点兼容性**：各家 OpenAI 兼容实现细节有差异（鉴权头、模型列表格式）→ 统一走标准 `/chat/completions` + Bearer key，探活失败诚实降级，不臆造可用
6. **密钥泄漏（C 方案新增风险）**：key 绝不能进日志/产物/异常堆栈/前端明文回显 → 独立 backend.json + 读端点脱敏 + 写端点空值不改 + 测试锁定
7. **纯文本 md 无真实颜色**：md 版只能靠符号标记区分，颜色仅在 html 版 → UI 默认引导用户看 html 版，md 版作为通用/可 diff 的补充
