## 一、用户诉求与本轮定位

用户 2026-11-17 明确提出：

> 「对内容核心提取，**不能造假**」

并就"不通过大模型能否实现知识核心提纯"展开讨论后拍板：

> **「补写保留，增加补写开关」**

因此本轮不是"要不要大模型"的技术选型，而是**把可信度分层写进产品契约**：

| 轨道 | 能力 | 可信度 | 默认 |
|---|---|---|---|
| **A 可信提纯** | 抽取式核心提取（原文原句 + 关键词 + 锚点 + 打分） | **架构级保证不造假**：每句都能在原文逐字定位 | ✅ 开启 |
| **B 原文内改写** | 措辞归并、术语统一、结构重排、要点去重 | 只用原文素材，不引入外部事实 | ✅ 开启 |
| **C AI 补写** | 补上原文没有的内容 | **按定义即生成物**，无法保证不造假 | ❌ **开关默认关闭** |

**核心裁决**：C 档保留但默认关闭，用户显式开启即视为知情同意；开启后 C 档内容**强制隔离**在独立分区并标注「模型生成，请核对」，绝不与 A/B 档混同。

---

## 二、为什么抽取式是"降风险"而非"降级"

S7 的 LLM 提纯靠**校验兜底**防编造（无效锚点观点丢弃）。抽取式则是**结构上不可能编造**：

- 输出句子是原文的**原样子串**（只做首尾空白裁剪与换行归一，不改词序、不改字）；
- 块级锚点必然有效 → S7 那道校验防线在 A 档下**恒通过**，不需要额外校验；
- 附带 LLM 给不出的东西：**打分与理由**（中心度 / 标题共现度 / 位置权重），让用户知道"这条为什么是核心"。

同时抽取式**零依赖、零下载、离线可用**：客户装 exe 即用，不需要装 ollama、不下模型、不填 key。

## 三、A 档技术方案（纯标准库，零第三方）

| 环节 | 算法 | 选型理由 |
|---|---|---|
| 分词 | **字符二元组切分** + 中文停用词表 | 规避第三方分词器（jieba 等），二元组在中文关键词抽取上效果接近词级，且零依赖 |
| 关键词 | **TF-ICF**（逆类别频率）+ 位置/共现加权 | 长文档里 TF-IDF 的 IDF 饱和，ICF 更稳；ICF 用"块"作类别，天然贴合分块结构 |
| 短语 | RAKE 式停用词切分 + **二元组词形归并** | 抽取"核心提纯"这类固定搭配，比单词更有信息量 |
| 句子打分 | **TextRank**（句子相似度图 + PageRank 幂迭代） | 经典无监督中心度；纯 Python 可实现，无需 scipy/numpy |
| 结构加权 | 标题共现度 + 位置先验（段首/段尾/列表项） | 技术文档的知识点密度不均，标题与列表项权重高 |
| 去冗余 | **MMR**（最大边际相关） | 避免选出三句同义的话 |
| 可回溯 | 每条核心带 `block_anchor` + 原文出处 | 与 S7 的 8 字段 src 注释、块级锚点体系一致 |

**输出形态**：每条核心 = `{原文原句, 关键词列表, 块锚点, 打分}`，打包成 `.refine.md`。

## 四、B 档原文内改写（只动结构与措辞，不动事实）

允许的操作白名单（**超出白名单一律不做**）：

1. **术语归一**：同一概念在文中出现的多种写法，统一到出现频次最高的写法（记录被归一的写法）；
2. **要点合并去重**：语义高度重叠的两条要点（字符 bigram Jaccard 相似度超阈值）合并为一条，保留块锚点并列；
3. **结构重排**：按块号顺序或章节层级重排要点，不增删内容；
4. **空行/标点归一**：仅做排版层面的空白与全半角标点统一。

**禁止**：改写事实、添加解释、生成结论、调整数字/单位/人名/日期。

## 五、C 档补写与开关

| 项 | 约定 |
|---|---|
| 开关位置 | 后端配置（`backend.json`）中的 `allow_suppplement` 布尔项，**默认 `false`** |
| 存储 | 与后端配置同文件；不新增配置文件 |
| 生效条件 | 仅当 `allow_suppplement=true` **且** 已配置可用 LLM 后端（Local/Cloud）时才启用；任一不满足 → 不产出补写内容 |
| 产物隔离 | 补写内容单独分区「AI 补充（模型生成，请核对）」，与 A/B 档核心分区**物理分开**，独立标题、独立标记前缀 |
| 标记 | 沿用 S7 修订标记语法，但补写项统一用 `[++ … ++]`（新增）并额外带 `AI` 前缀标签 |
| 诚实告知 | 产物头部必须含「本文件含模型生成内容，仅供参考，请核对原文」字样 |
| 可追溯性 | **补写内容不声明块锚点**（它不对应任何原文块）→ 这正是它与 A/B 档最直观的区分 |

> **诚实边界**：补写无法做到"不造假"，只能做到"明确标注 + 与原文物理隔离 + 用户显式开启"。这是产品诚实性的底线，不是技术缺陷的遮羞布。

## 六、能力命名与产物

| 能力 | 名称 | 产物 | 说明 |
|---|---|---|---|
| 可信提纯 | `extract`（后端类型 `extract`） | `out/derived/<doc_id>.refine.md` | A+B 档主线，零依赖 |
| 原文内改写 | 并入 `extract` 档 | 同上 | 白名单内的结构/措辞调整 |
| AI 补写 | `supplement`（开关） | 同上，独立分区 | C 档，需 LLM 后端 + 开关开启 |

**后端类型枚举扩展**：`none` / `local` / `cloud` / `extract`。`extract` 是**内置后端**，恒可用、零配置、无需探测外部进程——它不是"用户配置的后端"，而是"永远存在的兜底引擎"。

## 八、红线（不可越过）

1. **A/B 档输出必须能在原文中逐字定位**——机器可验证，不靠"模型自觉"。
2. **B 档操作必须在白名单内**——超出即不做，绝不"顺手润色"改事实。
3. **C 档默认关闭**；开启后强制隔离标注，绝不与原文核心混同。
4. **不引入任何第三方依赖**——分词、图算法、相似度全部纯标准库。
5. **产物只落 `out/derived/`**，冻结对账盘只读。
6. **零下载、零打包、零自动安装**——`extract` 档让"装 exe 即用"成立。
