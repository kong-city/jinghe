## 更新：S12a 已落地（2026-11-22）

用户裁决采用架构师默认推荐：① 应用内调度（方案 B）+ 启动补跑，核心调度无关；② 订阅源通用 URL + 可选 cookie（不绑特定平台）；③ 接受「关窗即停、下次补跑」；④ 提纯默认不造假。直播部分按用户要求待定。

**S12a 交付（手动触发闭环）**：

| 模块 | 实现 |
|---|---|
| `subscription_store.py` | 订阅注册表落盘（`%LOCALAPPDATA%\Jinghe\subscriptions.json`），last_seen 指纹、due 判断、失败计数/自动停用、脏数据保守校验、原子写入 |
| `channel_discovery.py` | yt-dlp `--flat-playlist --dump-single-json` 只枚举不下载；URL 形状预检 + cookie 只读；解析去重、失败诚实降级；复用 `link_media.capability()` 判 yt-dlp |
| `subscription_engine.py` | 增量编排：发现→差集→link_guard 门禁→yt-dlp 下载→S4 转写→kb.ingest_md→回写 seen_ids；两层去重（seen_ids + content_hash）；单实例串行、可取消、失败隔离、临时目录清理；全部依赖可注入 |
| app.py / UI | 5 个 API 端点 + 知识库页订阅区块；能力边界如实披露（需 yt-dlp、cookie、公开内容、不支持视频号/直播） |
| 测试/构建 | `test_subscription.py` 10 项；build.spec / CI / 门禁编译清单同步 |

**验收**：218 项全量测试 OK（新增 10 项）；发版门禁 16/16；四轮自我迭代发现并修复 2 个真实缺陷（UI 契约字符串断言、yt-dlp 能力探测函数名）；API 端到端实测增删改查/幂等/诚实降级全通过。

**未做（后续阶段）**：定时调度器常驻轮询（S12b）、直播回放专门支持（S12c）、系统级常驻服务（方案 A，待裁决）。一期为手动触发 + 启动补跑。

## 一、对标功能的产品本质（先把「它到底是什么」说准）

依据官方文档 `doc.biji.com/docs/DbLDwXMG3i3db7kivWpcDJrJnqe/` 与 `biji.com/docs/getnote/knowledge-base/create`，得到大脑的该功能拆开是四件事：

| 环节 | 得到大脑的做法 | 关键事实 |
|---|---|---|
| 订阅入口 | 知识库详情页 →「订阅直播/博主」 | 抖音博主＝粘贴**个人主页链接**；视频号＝上传**博主主页截图**（无公开链接）；得到直播/视频号直播＝上传直播链接或预约截图 |
| 定时追踪 | 云端托管定时任务 | 抖音订阅：每天早上 8 点更新博主**前一天**发布的最新短视频 |
| 内容处理 | AI 全自动 | 转写 → 摘要 →「类似罗老师学习笔记」的**专业模板**；直播用专门模板，普通链接用通用模板 |
| 知识沉淀 | 归入专题知识库 | 可对这个库搜索、提问、二创；视频号单条短视频因无可分享链接，**只能靠订阅博主**间接获得 |

**本质**：这是一个「**频道订阅 + 增量拉取 + 云端 AI 加工 + 知识库沉淀**」的闭环。它解决的核心痛点是「我不必每天去刷博主主页，系统把新知识自动送进我的库」。

**产品形态的关键洞察**：得到大脑能做到「每天 8 点自动更新」，是因为它是**云端常驻服务 + 拥有平台数据接口/授权**。这两点恰好是 jinghe 的架构底座**没有**的——这是整个移植分析的分水岭。

## 二、jinghe 现状能力盘点（哪些能直接复用）

jinghe 不是从零起步。S5 已经解决了「给一个视频链接 → 提取成带锚点的 md」这条最难的链路：

| 现有模块 | 已具备能力 | 对本功能的复用价值 |
|---|---|---|
| `link_guard.py` | URL 形状校验、私网 IP 拦截、DNS 解析、重定向链校验（防 SSRF） | ★★★ 频道发现后的每个视频 URL 都走它，安全边界现成 |
| `link_downloader.py` | 调本机 `yt-dlp`；`--no-playlist` 逐条调度；cookie 只读引用；时长/大小/超时/取消全控 | ★★★ 单个视频下载完全复用；**播放列表枚举要新建**（现有刻意关掉了 playlist） |
| `link_media.py` | 批量任务、进度事件、取消、临时目录清理、复用 S4 handler 出 md | ★★★ 现成的 Job 模型，订阅批次可直接套用 |
| `video_transcribe.py` | S4 独立视频 handler，三区块产物 + 锚点 + provenance，绝不复用音频路径 | ★★★ 转写出 md 的环节零改动 |
| `iterate_engine.py` | S11 多轮提纯，共识焦点逐轮重排，不造假 | ★★☆ 可选：作为「摘要/要点」的抽取式实现（无 LLM 时的诚实降级） |
| `kb.py` | sqlite3 + FTS5 知识库；`parse_md_entries` 解析锚点条目；`ingest_md` 用 `content_hash` + id **幂等去重** | ★★★ 入库与去重是现成的，天然支持「重复订阅不重复入库」 |
| `backend.py` | 本机 ollama / 云端兼容端点，可插拔 | ★★☆ 对标得到大脑的「AI 加工」，但 jinghe 默认离线不造假 |
| app.py 设置/Job/看门狗 | settings.json 落盘、单实例、关窗回收进程树、长任务超时看门狗 | ★★★ 订阅注册表落盘、调度线程都能挂在这套机制上 |

**结论**：真正**从零新建**的只有两层——「订阅管理/频道发现」和「调度编排」。视频下载、转写、提纯、入库、去重全部可复用。这是这个项目最大的有利条件。

## 三、决定性的架构分歧：云端托管 vs 关窗即退

这是必须在立项阶段就拍板的问题，否则做出来一定是「假功能」。

- 得到大脑：7×24 云端定时，你不打开 App 它也在更新。
- jinghe：本地桌面软件，`关窗即退` 是写进契约的硬约束（v1.1.5–v1.2.0 花了多个版本做进程回收，确保关窗后端口和子进程归零）。

三种落地方案的权衡已在架构对比图中给出，结论复述：

| 方案 | 可用性 | 与 jinghe 契约的冲突 | 决策 |
|---|---|---|---|
| A 系统常驻服务（计划任务/tray） | 真 7×24 | **直接冲突**：违背关窗即退、零残留、安装卸载复杂度陡增 | 否（一期） |
| B 应用内调度 + 启动补跑 | 运行时更新，补齐遗漏 | 无冲突：复用现有 Job/看门狗，零新增进程 | **推荐为一期基线** |
| C 外部触发器（cron 调 CLI） | 取决于用户配置 | 无冲突，但要求用户自建调度 | 二期可选高级入口 |

**一期架构原则**：把「订阅 + 增量拉取 + 入库」做成**与调度外壳解耦的可复用核心**。这样 A/C 以后要加，只是换一个触发外壳，核心不用重写。

## 四、目标架构设计（一期，方案 B）

### 4.1 新增模块（独立文件，遵守「冻结内核 + 独立模块」纪律）

| 新模块 | 职责 | 关键接口（建议） |
|---|---|---|
| `subscription_store.py` | 订阅注册表落盘 `%LOCALAPPDATA%\Jinghe\subscriptions.json`；字段：id、平台、源 URL/截图路径、显示名、启用态、轮询间隔、上次拉取时间、last_seen 指纹集合 | `add/list/remove/update_seen/mark_polled` |
| `channel_discovery.py` | 频道发现：用 `yt-dlp --flat-playlist --dump-json <主页>` 枚举频道最近 N 条视频的 id/URL/标题/发布时间；**不下载** | `discover(source, limit) -> list[VideoRef]` |
| `subscription_engine.py` | 编排核心：对每个订阅 → discover → 用 last_seen 差集算出「新视频」→ 逐条走 link_guard → link_downloader → video_transcribe → iterate_engine（可选）→ kb.ingest_md → 更新 last_seen。带取消、进度事件、失败隔离 | `run_due(force=False)`, `status()`, `cancel()` |
| `subscription_scheduler.py` | 应用内调度线程：启动时补跑 due 项，运行中按 interval 定时触发；进程退出时随主线程结束 | `start()`, `stop()` |

### 4.2 数据流（一条新视频的完整旅程）

```
订阅源(discover) → VideoRef{id,url,title,published}
   → 差集过滤(last_seen) → 新视频
   → link_guard.check_link        [SSRF 安全门]
   → link_downloader.run_download [yt-dlp + cookie 只读]
   → video_transcribe.transcribe  [S4 三区块 md，带锚点]
   → iterate_engine.iterate_core  [可选提纯；不造假]
   → kb.ingest_md                 [content_hash 幂等去重，二次保险]
   → subscription_store.update_seen(id)
```

**两层去重是刻意设计**：`last_seen` 指纹集合避免重复下载（省流量），`kb.content_hash` 避免重复入库（保知识库干净）。二者互不依赖，任一层失效另一层兜底。

### 4.3 与现有模块的接线

- **API**（app.py，无新增端点类别，沿用风格）：`/api/sub/add`、`/api/sub/list`、`/api/sub/remove`、`/api/sub/run-now`、`/api/sub/status`。
- **UI**：知识库页加「订阅」区块（对标得到大脑在知识库详情页添加订阅的位置）；复用现有设置页的 cookie 配置入口。
- **构建**：4 个新模块加进 `build.spec.hiddenimports`；新测试 `test_subscription.py` 加进 CI 与门禁编译清单（沿用 S11 的教训）。
- **版本**：按契约每改一次代码 patch 升号；本功能属新能力，正常应走 minor，但用户已裁决「一律 patch 制」，从 v1.2.1 起逐 patch 递增。

## 五、能力边界与合规红线（诚实披露，不假装能做到）

这是架构师必须提前讲清的部分，也是得到大脑与 jinghe 差距最大的地方：

| 平台/场景 | 得到大脑（云端 + 授权） | jinghe（本地 + 零依赖）可行性与边界 |
|---|---|---|
| 公开视频站点（B站/YouTube 等 yt-dlp 支持） | 支持 | **可行**：`--flat-playlist` 枚举 + 逐条下载，完整复用现有链路 |
| 抖音博主主页 | 粘贴主页链接，云端解析 | **受限**：需用户提供本机 cookie；平台反爬/DRM 时不保证成功，失败要诚实降级，不绕验证码/DRM（现有 S5 契约已明确） |
| 视频号博主 | 上传主页截图识别 | **不可行**：无公开可分享链接 + 截图识别依赖云端视觉模型。jinghe 的合理替代是让用户订阅**可公开访问的主页 URL**，截图订阅明确不做 |
| 直播实时流 | 上传直播链接/预约截图，AI 边听边记 | **不可行（一期）**：直播是实时流，依赖云端录制与推流授权。可退化为「**直播回放链接**」的标量处理——回放是普通视频，现有链路可直接吃 |
| 得到站内独家内容 | 平台自有授权 | **不可行**：无授权，不做 |

**产品语言必须诚实**：UI 上写「订阅公开视频主页 / 直播回放链接」，而不是照抄得到大脑的「订阅直播/博主」——否则用户预期会被误导。

## 六、风险登记

| 风险 | 等级 | 缓解 |
|---|---|---|
| 平台反爬 / cookie 失效导致订阅静默停止 | 高 | 拉取失败在订阅列表显式标红 + 事件日志；连续失败 N 次自动停用并提示，绝不假装成功 |
| 定时轮询占资源 / 与手动任务抢带宽 | 中 | 单实例串行队列（复用现有 Job 互斥）；间隔默认 24h 且可配；只对 due 项拉取 |
| 播放列表枚举触发限流 | 中 | discover 限速 + limit（如最近 20 条）；last_seen 差集保证只下新的 |
| 「关窗即退」被调度线程破坏 | 高 | 调度线程设为 daemon，进程退出随主进程结束；复用现有进程回收，不 spawn 常驻子进程 |
| 版权 / 服务条款 | 中 | 定位为「对用户有访问权限的公开内容做本地知识整理」，不绕 DRM、不分发内容、不内置凭证 |
| 新增模块漏进构建/CI | 中 | 按 S11 教训同步 build.spec、CI unittest、门禁编译清单，并加接线契约测试 |

## 七、分阶段路线图（建议）

## 八、结论与待用户裁决

1. **可移植性结论**：约 70% 能力（下载/转写/提纯/入库/去重/安全）已在 jinghe 中现成，真正新建的是「订阅管理 + 频道发现 + 调度编排」三层。技术风险主要在平台侧（cookie/反爬），不在 jinghe 自身架构。
2. **最大架构分歧**：得到的云端 7×24 无法照搬；一期建议方案 B（应用内调度 + 启动补跑），并把核心做成调度无关。
3. **必须诚实的能力边界**：视频号截图订阅、实时直播、平台独家内容不做；抖音依赖用户 cookie 且失败要显式降级。
4. **待裁决（开工闸门）**：
   - ① 是否认可方案 B 作为一期基线？
   - ② 一期支持的平台范围：仅公开站点，还是包含抖音（cookie 依赖）？
   - ③ 是否接受「关窗即停、下次启动补跑」与得到大脑「云端常驻」的体验差异？
   - ④ 提纯环节默认走 S11 抽取式（不造假）还是可选 LLM 摘要？建议默认抽取式，LLM 作为可插拔增强。

> 按项目纪律：本分析为立项文档，裁决通过后再进入 S12a 施工、逐项验收并 patch 升号。
