## 二、白盒代码审计

- **命令注入面**：全项目（排除测试）**零** `shell=True` / `os.system` / `eval` / `exec`；24 处 `subprocess` 调用全部为 argv 列表形式，无 shell 解释。
- **SQL 注入面**：`knowledge/kb.py` 全部 `conn.execute` 使用参数化占位符；FTS 表名固定构造，不接用户输入。
- **请求体上限**：`_read_json` 限制 8MB（`app.py:2512`），超过直接拒绝。
- **CSRF 三道校验**：Content-Type 必须 application/json、Origin 必须本机、Host 必须本机（GET/POST 都查），实现于 `_check_write_request` / `_check_host`。
- **路径围栏**：所有产物打开/入库端点复用 `_kb_allowed_roots()` + `Path.resolve()` 规范化 + `kb._is_within()` 双重校验。本轮新增 `/api/pipeline/finish` 亦走同一围栏。
- **新增端点回归**：v1.6.0 的三个新能力（一键流水线 / 便携运行时 / S12c）未引入新的网络暴露面；便携运行时下载仍受手动令牌保护（无令牌必拒，已由 test_v160_features 守护）。

## 三、附注（未真正执行项，非漏洞）

- T9：使用了不存在的端点名 `/api/preview`，实际入口不同；命令注入面已由白盒审计（零 shell=True）覆盖，风险已排除。
- T15：测试脚本向 `/tmp/big.json` 写载荷时该路径在 Windows Git Bash 下不存在，实际发出的是空 body；代码白盒审计确认 8MB 上限存在，DoS 防护有效。

## 四、结论与建议

本轮未发现可利用安全漏洞。现有防线（CSRF 三校验、SSRF IP 白名单、路径双重围栏、SQL 参数化、零 shell 执行、API Key 脱敏、body 上限）均验证有效。建议保持：
1. 任何新增 POST 端点必须位于写请求校验分支内（本轮 `/api/pipeline/finish` 已符合）；
2. 任何新增路径参数端点必须走 `_kb_allowed_roots()` 围栏；
3. 便携运行时等下载能力必须持手动令牌，禁止探测路径触发。
