> 分析日期：2026-11-26　　基线：v1.7.1
> 方法：全链路代码探查 + 关键点逐条核验（非泛泛而谈）
> 相关背景：[CID乱码PDF诊断改进-说明.md](CID乱码PDF诊断改进-说明.md)、[发版前验证清单.md](发版前验证清单.md)

## 一、先搞清楚"转化"走哪条路

精核的 PDF 转化**主程序零第三方依赖**，PDF 解析是完全自研的，OCR 是可选外挂。链路：

```
/api/run (app.py:3061)
  → 子进程跑 extract.py（打包态跑冻结的 Jinghe.exe --cli）
    → _builtin_rich_extract() → .pdf 分支 → _pdf_extract() (extract.py:1475)
      → 对象扫描 → ToUnicode CMap → 字体码宽解码 → 坐标系还原 → 质量门禁
    → 产出 md + doc_id/sha256 锚点 + provenance.json
  → OCR 后处理 (app.py:1755-1783)：组件可用时对 PDF 再跑一遍 OCR
```

关键约束：`CAPABILITY_CONTRACT.md:28` 规定 **extract.py 主流水线冻结，一行不动**，所有增强只能落在 app.py 后处理层。下面区分"内核层"和"后处理层"讲。

## 二、转化结果受哪些因素影响

### A. 源文件侧（决定天花板）

| 因素 | 影响 | 代码依据 |
|---|---|---|
| **是否有文字层** | 无 `BT`+`Tj/TJ` 判为扫描件，直接不产出 | extract.py:1493 / 1541 |
| **ToUnicode CMap 完整性** | 子集字体缺映射 → CID 乱码，触发 `PDF_CID_NEEDS_SPECIALIST` | extract.py:1183 / 1501 |
| **字体资源名唯一性** | F1/F2 同名不同字体不按页隔离，以最后出现的为准 → 错用 CMap | extract.py:1044-1059（注释自陈"实用近似"） |
| **流压缩格式** | 只支持无 Filter 和 FlateDecode；ASCII85/LZW/DCT 直接降级返回 None | extract.py:1010-1022 |
| **页面变换矩阵** | `1 0 0 -1 cm` 翻转、`ta/td` 缩放（WPS 0.05 缩放致 x 放大 20 倍）都要补偿 | extract.py:1366-1368 / 1437 |
| **文件大小** | >100MB 判"需拆分" | extract.py:94 / 1899 |

### B. 解析算法侧（决定还原度）

| 因素 | 默认值 | 影响 |
|---|---|---|
| 质量门禁 | 正文≥40 字 且 合理字符占比≥0.6（extract.py:1522-1531） | 占比是硬阈值二值判断，不输出分数；0.6 以下直接判失败 |
| 合理字符集 | CJK/中文标点/全角/ASCII（1517-1519） | 刻意排除 Latin-1 补充区（乱码高发区），但会误伤合法拉丁文 |
| ToUnicode 缺码位 WARN 阈值 | 5%（1507） | 只打日志不改状态，注释明确"提阈值会误伤正常子集字体" |
| 行基线聚合容差 | 2.0（1441） | 容差不当会串行或断行 |
| TJ 数组处理 | 只收 `str`/`hex`（1407-1421） | **忽略数字 kern** → 词间空格不插入 |
| 阅读方向 | 首末 run 推断（1437-1438） | 旋转/混合方向页会乱序；无 `cm` 旋转、无 CropBox 处理 |

### C. OCR 侧（组件可用时叠加）

| 因素 | 默认值 | 影响 |
|---|---|---|
| 渲染 DPI | `fitz.Matrix(2,2)` ≈ 144dpi（ocr_worker.py:60） | 硬编码，低清扫描件可能不够 |
| OCR 引擎 | RapidOCR 默认参数，无语言/模型配置（ocr_worker.py:53） | 无版本锁定（components.py:170），历史发生过 onnxruntime DLL 初始化失败 |
| 置信度 | **被丢弃**（只取 item[1]，ocr_worker.py:65） | 无法区分"认清了"和"蒙对了" |
| 触发条件 | 组件可用就对所有 PDF 跑（app.py:1763） | 但跳过阈值 40 字（pdf_ocr.py:136）：部分乱码但过了 0.6 门禁的件会被**当成成功跳过 OCR** |
| 页数上限 | max_pages=0（全部），API 未暴露 | 431 页大件耗时可控但无分级 |
| 子进程超时 | 900s（pdf_ocr.py:111） | 大件可能超时 |
| 文本清洗/质检 | `clean_ocr.py`/`check_ocr_quality.py` **未接入运行时** | 水印、断行、误识、单字碎片全保留 |

### D. 结果组织侧

| 因素 | 现状 | 影响 |
|---|---|---|
| **PDF 页码锚点** | `loc["page"] = n` 用的是 Markdown 标题块序号（extract.py:545-546） | PDF 解析几乎不产标题块 → 整篇只有 1 个块、page 恒为 1；`_pdf_page_contents()` 已按页切分但页码在拼接时丢弃 |
| 表格/图片 | PDF 路径完全无处理 | 表格结构丢失，图片不提取 |
| OCR 产物溯源 | 直接写 `outdir/<stem>.md`（pdf_ocr.py:133/139） | 无 doc_id / src 注释 / provenance 记录 → 扫描件"成功 0" |

## 三、值得优化的方向（按收益/成本排序）

所有建议都遵守"内核冻结"约束——优先落在 app.py 后处理层或可选组件，不动 extract.py 主流水线。

### 高收益 · 低成本（建议先做）

1. **把离线 OCR 质检/清洗接入运行时**
   `clean_ocr.py`（水印过滤 + 11 条高置信误识修正）和 `check_ocr_quality.py`（6 项指标）现成的，全项目无运行时调用。在 `pdf_ocr.ocr_pdf_to_md()` 写出前可选调用，并输出质量报告。**不动内核**。

2. **引入置信度门禁**
   `ocr_worker.py:65` 把 RapidOCR 的 `item[2]` 置信度丢了。保留平均置信度 + 复用 6 项质量指标做准入，低置信度页标黄让人复核，而不是无脑"非空即成功"。

3. **精确化 OCR 触发条件**
   现状：组件可用对所有 PDF 跑，但已有 >40 字 md 就跳过 → "部分乱码但过 0.6 门禁"的件被保留为成功。改为按 `provenance.json` 的降级状态（`PDF_CID_NEEDS_SPECIALIST` / 需先 OCR）精确触发，并提供"强制 OCR"开关。

### 高收益 · 中成本

4. **修复 PDF 页码锚点失真**
   `loc["page"]=n` 是伪页码，但 `_pdf_page_contents()` 本就按页切了内容流。在解析阶段保留页边界，让锚点携带真实页码；OCR 产物也补锚点。这直接提升知识库块级引用的可用性（思源式反链的定位精度）。

5. **OCR 产物纳入对账与溯源**
   给 OCR 产物写 `provenance_ocr.json`，补 doc_id/src 注释，在 UI 汇总区展示。解决扫描件"成功 0"的观感问题。

### 高收益 · 高成本（择机）

6. **补齐版面/表格能力**
   保留 OCR 的 bbox（现在也丢了）做版面还原与表格单元格重建；或参照 OCR 组件机制引入 `pymupdf4llm` 作为可选 markdown 解析器（打包态 markitdown 基本不可用，extract.py:1666-1675）。

### 中收益 · 低成本

7. **修字体资源名冲突**：按页隔离 `/Font` 资源字典，别让同名 F1 跨页串用 CMap。
8. **扩展流过滤器**：补 ASCII85Decode / LZWDecode 支持，减少"不支持即降级"。
9. **参数外置 + 版本锁定**：DPI、0.6 阈值、900s 超时、max_pages 全部硬编码；OCR 组件包不锁版本。可按组件机制外置，并把实际安装版本写进组件清单。

### 低优先级

10. **修 TJ 数字 kern**（词间空格）、**旋转/CropBox 处理**——边界情况，投入产出比低。
11. **消除文案漂移**：`app.py:2824` 注释仍写 tesseract+poppler（实际已移除）；内核错误归因因冻结不能改，L4 每次纠偏。可用结构化错误码统一映射。

## 四、风险提示与验证

- **内核冻结是硬约束**：任何改动 extract.py 主流水线的方案都要先过 `CAPABILITY_CONTRACT.md` 评审，别直接动。
- **质量门禁别轻易调阈值**：0.6 和 5% 都是踩过坑的 empiric 值，调高会误伤正常子集字体（代码注释有明确警告）。
- **OCR 组件版本不锁是历史故障源**：onnxruntime DLL 初始化失败就是因为装了不兼容版本，改前先锁版本。
- **验证方式**：改完跑 `test_v150_ocr.py`（11 项 OCR 守护）+ `test_extract.py` 的 test_26/27（CID 与诚实降级）+ 全量 435 项 + 门禁 16 项。跑全量前先清残留进程，避免偶发超时（见发版前验证清单）。
