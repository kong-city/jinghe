## 一、需求确认表

### 1.1 原始需求（用户原话拆解）

| 编号 | 诉求 | 交付形态 |
| --- | --- | --- |
| N1 | 增加 Word 转换为 `.md` | 见 1.2 的歧义澄清 |
| N2 | 音频转换为 `.md` | 带时间戳的转写文档 |
| N3 | 视频转换为 `.md` | 音轨 + 画面/字幕 + 元数据 |
| N4 | 给视频链接，提取对应视频内容转换为 `.md` | 链接解析 + 本地化后走视频链路 |
| N5 | 开发步骤分成小阶段，完成后进行确认 | S0–S6 逐阶段闸门 |

### 1.2 歧义澄清（S0 必须先钉死）

- 「Word 转换为 `.md`」方向有歧义：`.docx → .md` **早已支持**（`extract.py` 走 `zipfile` + OOXML，带 8 字段 `src` 注释与 `heading_path` 锚点）；项目里长期挂的「Word 后续计划」其实指 **`.md → .docx` 导出**（`ui/index.html:118` 的「导出 Word（规划中）」为禁用占位）。
- 用户已选「**两者都要**」：S2 拆成 **S2a 输入增强**（`.doc` 旧格式、批注/修订/加密识别）与 **S2b 导出**（纯标准库 `zipfile` + OOXML），分别验收。

### 1.3 用户已确认的四项决策

| 决策 | 选择 | 对计划的实质影响 |
| --- | --- | --- |
| 确认粒度 | **逐阶段确认** | 每阶段跑通验收即停下等确认；本轮 S0 完成后即停 |
| Word 方向 | **两者都要** | S2 拆 S2a / S2b 两个子阶段 |
| 引擎策略 | **本机可插拔工具** | ffmpeg / whisper / yt-dlp 由本机提供；统一接口 + 健康探测 + 缺工具诚实显示「未启用」；绝不伪转写 |
| 链接范围 | **任意链接与播放列表** | S5 范围最大：白名单 + 防 SSRF + 重定向收敛 + m3u8/DASH + 批量任务队列 |

### 1.4 范围与非目标

- **做**：N1–N4 四类能力、能力框架地基、逐阶段验收与发版。
- **不做**：云 API 转写（用户已排除）、绕过平台鉴权 / 付费 / DRM、把模型或外部 CLI 冻进 exe、阶段 4 知识库、深度语义摘要（LLM）、修订 `SPEC.md`、把音视频并入阶段 1 分流。

## 六、对上一轮路线图的两处精化（诚实标注）

架构图纸在 S0 精确对账后有两处需要收紧，均以「冻结内核不动」为准：

1. **`test_06` / `test_11` 不改写**。路线图曾写「改写 `test_11` 为新契约」；对账后确认这两个测试守护的是 `extract.py` 阶段 1 分流，一旦改写就等于动冻结内核。正确做法：**原样保留**，另在 S4 新增独立测试守护「新 video handler 不得复用音频路径」。
2. **产物不落 `INDEX/MERGED` 对账盘**。路线图曾写「落 INDEX/MERGED/provenance 三处留痕」；但 `SPEC.md:122` 要求 `md/*.md` 实盘双向对账，直接写入会让件数不平、多条黑盒断言失败。正确做法：落独立 `out/derived/` + `provenance_media.json`，自带来源注释与锚点，**不改写** `INDEX.md` / `MERGED.md`。
